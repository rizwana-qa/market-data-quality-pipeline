# Interactive market intelligence report

The daily run publishes one interactive HTML report per analysis date to GitHub Pages and links it from the success e-mail.

    https://rizwana-qa.github.io/market-data-quality-pipeline/reports/<YYYY-MM-DD>/market_intelligence_report.html

Older dates stay online (`keep_files: true`). The same file is the fourth deliverable of the workflow artifact, so it is also the fallback.

## The approved v4 design (golden reference; no longer the production default, see v6 below)

`src/interactive_report_template.html` (`design="v4"`) is the approved v4 report (`tests/fixtures/market_intelligence_report_2026-11-12_v4_release.html`, SHA-256 `03e68097...f1e30ae`) with every data-dependent token replaced by a named `{{slot}}`.
Everything else (layout, CSS, JavaScript, charts, tooltips, fixed wording) is byte-for-byte v4, except for the five wording regions below. `src/interactive_report.py` fills the slots from one validated CSV; the same numbers feed the visible text and the embedded `report-data` JSON.
The golden test renders `tests/fixtures/report_2026-11-12_data.csv` and compares it with the approved file: for a supplied CSV exactly three blocks differ (the hero label "UTC DAY", the source note and one added paragraph), and for an automated fetch five (those plus the fetch-time line and the footer); the stylesheet, the chart script and the structure are byte-identical.

## Design v6: the final detailed report (production default)

`render(dataset, provenance)` now produces **v6**, the coral-led institutional report. v4 (the approved golden fixture) and v5 (the Phase 1 design) stay selectable with `design="v4"` / `design="v5"` for comparison and for their own tests; `tests/test_interactive_report.py` still pins v4 byte for byte.
It is generated by the same architecture as before (`daily_automation.py build-interactive-report` -> `interactive_report.render` -> `src/interactive_report_template_v6.html`) and is one standalone file of about 4.9 MB: the vendored Plotly.js (SHA-256 checked, as in `dashboard.py`), the dashboard's own validated logic block, and the strict dashboard CSP (`default-src 'none'`, script hashes, `connect-src 'none'`). `MAX_INTERACTIVE_REPORT_BYTES` and `MAX_PAGES_REPORT_BYTES` in `daily_automation.py` were raised to 16 MB for that reason (the same bound as the dashboard).

**Reuse, not duplication:** the page's chart specifications, row selection, pagination and CSV export are the `/* LOGIC-START */ ... /* LOGIC-END */` block of `src/dashboard_template.html`, extracted at render time (a test asserts it is byte-identical). Chart data comes from `dashboard.window_slice / window_metrics / window_display`. The report's BTC / ETH colours are applied through `DashboardLogic.COLORS`. The export is the dashboard's contract: exact CSV values, date order, `report_<date>_data_last<k>days.csv`.

**Sections:** 01 executive intelligence (assessment, latest closes, up to three key findings, performance overview, monitoring), 02 performance, 03 risk and volatility, 04 trading activity, 05 the dashboard's four Plotly charts with window and asset controls, 06 Market Intelligence and Rule-Based Analysis, 07 data quality and methodology, 08 detailed data (all 17 columns, column groups, row-window filter, sorting, pagination, CSV export).

**Findings rule:** key findings are selected only by existing, approved thresholds: a 30-return gap of 5 percentage points (`MATERIAL_MOVE`), the R2 volatility-ratio limits, the 1.25x highlight level, and R1 "weak" co-movement. They are ranked by their ratio to the threshold; fewer than three are shown when fewer qualify. The proposed 10% drawdown and 2.5-standard-deviation levels are **not approved**: they appear only under the "Exploratory (proposed)" tab, labelled as such, and never select a key finding or change R1 to R3.
**Not claimed:** the report uses no AI model and says so; it states no generation time (the build is deterministic) and no fetch time unless the pipeline's own report recorded one.
**Design tokens** (documented in the template's `:root`): page `#F2F4F7`, card `#FFFFFF`, navy `#142C54` / `#203D68`, coral `#E8796B` (fills and accents; text uses `#B23F30`), BTC `#3478C8`, ETH chart mark `#DD6551` (a slightly deeper coral than `#E8796B`, which is only 2.85:1 on white), amber `#D99A32` (text `#8A5A00`), secondary text `#5A667A` (the suggested `#667085` is 4.5:1 on the page background, below AA on tinted surfaces).

## Design v5 (Phase 1 redesign, superseded by v6; kept for comparison)

`render(dataset, provenance, design="v5")` fills `src/interactive_report_template_v5.html`. The default stays `DEFAULT_DESIGN = "v4"`, so the daily workflow, the staging re-render and every v4 golden test are unchanged until the v5 preview is reviewed and approved; the switch is then one constant plus a new golden baseline (the v4 fixture stays as the comparison reference).
v5 keeps all content, charts, controls and the dashboard link, and feeds the embedded chart data from the same code (byte-identical `report-data` JSON). It stays one standalone, dependency-free file (inline CSS, JavaScript and SVG, no request of any kind).

**Methodology changes (v5):**
- The close's position in the day's range is called **range position** (0% = the day's low, 100% = the day's high), not a percentile.
- **Current** drawdown (latest close against the window peak) and **maximum** drawdown (deepest value in the window) are shown separately, with the window-peak date. The page states that a higher close before the window cannot be seen, and says when the peak is the first close of the sample. Chart drawdown is re-based to the start of the selected window, and the subtitle says so.
- **RSI:** the simple-average RSI stays the primary reading. The **Wilder** RSI (first averages = plain means of the first 14 changes, then `(previous x 13 + change) / 14` over all 30 changes) is shown beside it as a labelled comparison, with a note that quotes both values and says whether they fall on the same side of the 35 / 65 marks.
- Provenance (UTC day basis, the recorded fetch time, the supplied-CSV wording) and its validation are unchanged.

**Presentation changes (v5):** the executive interpretation comes first; KPIs sit in four labelled groups (latest close, 30-return performance, drawdown, relationship and risk); a sticky section menu with the current section marked (`aria-current`) and a skip link; no text under 11 px (v4 used 8 to 10 px), AA text contrast, one BTC / ETH colour system (fill, chart mark and text ink defined once); tables scroll inside a focusable frame with a sticky first column on narrow screens; breakpoints at 1000, 760 and 480 px.

## Data provenance (what the report says about its data)

| Case | Hero line | Source note and footer |
|---|---|---|
| **Automated daily run** (`build-interactive-report`) | `AS OF <date> · UTC DAY` and `DATA FETCHED <time> UTC` | Kraken daily candles (one per UTC day), fetched automatically by the daily workflow on `<time>` UTC; all dates and day boundaries are UTC; "a completed UTC day ... not a real-time market feed" |
| **Manually supplied CSV** (`render(dataset)` without provenance) | `AS OF <date> · UTC DAY`, no fetch time | the approved v4 wording: "Supplied CSV representing Kraken spot OHLC daily records", "records no fetch time; its dates are taken as UTC days", "not a live market feed" |

The fetch time is never invented: the automated build reads it from the pipeline's own report (`Data fetched`, UTC), after checking that report against the CSV and that the time is a real date on the day after the analysis date; if it cannot be established the build is refused. A supplied CSV may not carry a fetch time. No generation time is stated: the report is built deterministically from the fetched data, and a clock value would break byte-for-byte reproducibility (the staging step re-renders the file and compares bytes).

`report_2026-11-12_data.csv` was rebuilt on 2026-11-14 from Kraken's public daily candles with the project's own fetch and CSV code. It is not the original upload; the 31 closes of both assets equal the closes embedded in the v4 report and the 12 November volumes and trade counts equal the v4 text.

## Metric definitions (all reproduce the v4 figures)

| Metric | Definition |
|---|---|
| Return over n | `close[-1] / close[-1-n] - 1`, n = 7, 15, 30 |
| RSI (14) | `100 - 100 / (1 + average gain / average loss)`, plain averages of the last 14 close-to-close changes |
| ATR (14) | plain average of the last 14 true ranges (`max(high-low, abs(high-prev close), abs(low-prev close))`); ATR / price uses the latest close |
| Realised volatility | sample standard deviation of the last n daily returns x sqrt(365); n = 14 and 30 |
| Turnover | volume x VWAP; ratios compare the latest day with the plain average of the 7 days before it |
| Average trade notional | turnover / trade count |
| Close vs VWAP | `close / VWAP - 1` |
| Close location | `(close - low) / (high - low)` as a percentile of the day's range; range / close = `(high - low) / close` |
| Maximum drawdown | lowest `close / running closing-price peak - 1` over the 31 closes; distance from the sample high and low use the latest close |
| Correlation | Pearson correlation of the 30 daily returns |

## Presentation rules that are not metrics

These are disclosed in the report itself (paragraph "Wording rules" in the methodology section, written from the same constants and checked by tests). Exact behaviour, verified against the code:

| Rule | Limit | Boundary |
|---|---|---|
| "materially above/below" their first closes | both assets' 30-return moves at least 5 % | inclusive |
| "elevated" activity, ratio highlight | 1.25 times the average of the previous seven sessions (the project's existing "clearly higher" mark) | inclusive; "above/below average" is more/less than 1.00 |
| "near the daily low / high" | close in the lowest / highest 25 % of the day's range | inclusive |
| "approximately at VWAP" | less than 0.05 % from VWAP | exclusive |
| RSI "near the lower / upper end" | 35 or below, 65 or above (both assets) | inclusive |
| co-movement "strong" / "moderate" | correlation size from 0.70 / from 0.30 | existing analysis limits |

The data-dependent sentences are chosen from fixed neutral patterns by comparing the computed numbers.
Where the approved v4 wording applies it is reproduced exactly; the other branches are symmetrical descriptions of the comparison and never predict.

## Price-jump (outlier) check: recommendation, NOT implemented

**Where it belongs:** `candle_rules.evaluate_window` (the shared rule set used by the producer, `dashboard.py` and `daily_automation.py`), as a new rule with its own id and instance in the expected-instance ledger, next to the existing candle rules. It must not live in the report generator.

**Evidence (read-only study of 720 daily Kraken candles per pair, 2024-11-26 to 2026-11-15; a snapshot, not a test fixture):**
- Largest genuine one-day close-to-close moves: BTC 13.9 % (2026-02-05), ETH 21.9 % (2025-05-08). A fixed cap of 25 % flags nothing historically (no false positives, but also almost no protection); a 10 % cap flags 2 BTC and 17 ETH real days.
- A robust rule (`|r - median30| > 10 x MAD30` and `|r| > 5 %`) flags 0 BTC and 1 ETH day of 689 (2026-08-19, a genuine +17.5 %); at 8 x MAD it flags 1 BTC and 3 ETH real days. Every flag in this sample is a genuine market event, so any such rule produces false positives on the days the report matters most.
- Cross-asset consistency: on all 45 days with a move above 7 % in either asset, BTC and ETH moved in the same direction, and the other asset moved more than 3.5 % on 35 of them; the "other asset moved less than a quarter as much" pattern occurred on 4 real days, so it is too weak to block on. No opposite-direction large move occurred (0 of 45), but a rule with no history to calibrate cannot be validated either.

**Recommended rule (warning, never blocking):** flag a day when an asset's close-to-close move exceeds both 10 x the robust daily sigma of the preceding 30 returns and 5 %, or when one asset moves more than 7 % against the direction of the other's move. Report it as a visible data-quality WARNING (in the report's governance section and the e-mail), not as a failed or INCONCLUSIVE candle result. Blocking would suppress the report exactly on genuine crashes, and the existing fail-closed rules (OHLC consistency, VWAP assumptions, same-data-in-both-pairs heuristic) already cover internally inconsistent candles.

**False-positive risks:** genuine one-day shocks (listing, protocol events, liquidation cascades), a quiet trailing window that makes the robust sigma tiny, exchange-specific outages or thin-liquidity prints that are real on that exchange, and a first-day-after-gap effect.

**Proposed tests (to write with the rule):** a genuine 14 % move that both assets share is flagged as a warning but the run still passes; a single 40 % candle in one asset with the other flat is flagged; an opposite-sign 8 % pair is flagged; boundary values at exactly 10 x sigma and exactly 5 % and 7 %; a window shorter than 30 returns raises no flag; an all-zero-variance window does not divide by zero; the warning text names the date, asset and size and appears in the report and the e-mail; the rule changes no sheet value and no existing validation outcome; the ledger plans and counts the new instances (none missing, duplicate or unexpected).
**Not established:** the true-positive rate (the sample holds no known bad candle) and behaviour on other exchanges. The thresholds above are therefore proposals to be reviewed, not implemented values.

## Request contract of `send_success_report`

Before: exactly the eleven keys `action, token, analysis_date, rows, run_id, workflow_url, validation_status, sheet_update, summary, artifact_url, report`.
After: the same, plus at most one of `report_url` or `report_link_status`. Both are optional; any other extra key is still refused.

* `report_url` must be exactly the Pages address of the request's `analysis_date`; `report_link_status` can only be `unavailable`.
* An invalid, mismatched or conflicting link field never blocks the e-mail: it is logged by reason code only (never the value) and the e-mail carries the validated artifact link instead.
* `self_check` additionally returns `report_link_supported: true`. The client sends the new fields only when it reads exactly `true`; it still requires `report_evidence_supported`.

## Workflow

`build_interactive_report` (from the validated CSV) -> `stage_deliverables` (four files, re-rendered and compared byte for byte) -> `prepare_pages` / `publish_pages` -> sheet steps -> artifact upload ->
`verify_pages` (HTTP 200 and the same SHA-256 on the exact address, bounded retries, never fails the run) -> `send_success_email` (`--report-link`).
A failed Pages publish still stops the run, as before. If verification does not succeed the e-mail carries the artifact link and says so.
